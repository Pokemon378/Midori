## Step 3 — Sensor Data API (simulated data)

**WHAT WE BUILT:** `POST/GET /zones/{id}/sensor-readings` and `GET .../latest`.

**WHY WE BUILT IT:** The data inlet of the intelligence pipeline. In this software-only MVP, readings are generated by software (a Digital Farm Simulator will POST here later); there is no hardware.

**HOW IT WORKS:** Strict Pydantic ranges — temperature −50…70 °C, humidity/leaf-wetness/soil-moisture/pest-activity 0–100, rainfall ≥ 0 — with required timezone-aware timestamps. Zone existence checked before insert; list endpoint supports limit 1–500, newest first.

**WHY IMPORTANT:** Impossible values are rejected at the door, so downstream features/risk never ingest garbage.

**NEXT MODULE CONNECTION:** Feature Engine consumes this table.

**TESTS:** `test_sensor_readings.py` — valid create, every range violation, nonexistent zone, latest/list ordering (15 tests).

## Step 4 — Feature Engine

**WHAT WE BUILT:** `GET /zones/{id}/features?window=30m|1h|6h|24h` producing statistical and trend features.

**WHY WE BUILT IT:** Risk scoring needs aggregated, comparable signals. The Feature Engine answers "What is happening?" — never "How risky?".

**HOW IT WORKS:** `service.py` queries zone+window-filtered rows (DB-level filtering, no full-table loads); `calculations.py` holds pure functions: current/avg/min/max per metric, rainfall total/count, leaf-wetness active duration above a configurable threshold, trend via earlier-half vs later-half average comparison with tolerance (`increasing`/`decreasing`/`stable`/`insufficient_data`), rate of change = (last − first)/elapsed hours.

**WHY IMPORTANT:** Deterministic, explainable features make the risk score auditable and reproducible.

**NEXT MODULE CONNECTION:** Risk Engine consumes this output directly.

**TESTS:** `test_features.py` — controlled timestamps/values for every statistic, trend classes, window filtering, 404s (14 tests).

## Step 5 — Risk Engine

**WHAT WE BUILT:** `GET /zones/{id}/risk?window=…` — deterministic 0–100 environmental risk score with levels, explainable reason codes, real trend history, and a camera-trigger decision.

**WHY WE BUILT IT:** To decide which zones deserve visual inspection without sending every zone to AI.

**HOW IT WORKS:** Weighted sum of configurable factor scores (humidity, leaf wetness value + active duration, temperature, rainfall, soil moisture, pest activity + trends, combination bonus), clamped 0–100. Levels: 0–24 LOW, 25–49 MEDIUM, 50–74 HIGH, 75–100 CRITICAL (configurable). Each assessment is persisted in `risk_assessments`; `risk_trend` is computed from that real history only. `camera_trigger=true` for HIGH/CRITICAL or rate spikes — a software decision only. Missing data → `risk_score: null`, `INSUFFICIENT_DATA`, camera never triggered.

**WHY IMPORTANT:** `camera_trigger` is the switch that makes image intake targeted instead of continuous.

**NEXT MODULE CONNECTION:** Images uploaded for triggered zones enter the Image Intake module.

**TESTS:** `test_risk.py` — all four levels, each reason code independently, trend classes, camera trigger true/false, insufficient data, 404/400 (25 tests).

## Step 6 — Camera/Image Intake + Image Quality

**WHAT WE BUILT:** `POST /zones/{id}/images` (multipart), `GET /zones/{id}/images`, `GET /images/{id}` with validation, safe storage, and quality checks.

**WHY WE BUILT IT:** To prepare images for future AI analysis and block unusable ones early.

**HOW IT WORKS:** MIME + real Pillow decode validation (JPEG/JPG/PNG/WEBP); SHA-256 hash; stored as `storage/images/zone_<id>/<uuid>.<ext>` — client filenames are sanitized for metadata only and never used for storage (path-traversal safe, no overwrites). Quality checks: minimum resolution (200×200), blur via Laplacian variance, brightness via mean grayscale — all deterministic, suitability-only, env-configurable. Statuses: `READY_FOR_AI` (accepted), `LOW_QUALITY` (valid but poor, with reasons), `REJECTED` (invalid → HTTP 400). Metadata lives in `image_metadata`; binaries on the filesystem.

**WHY IMPORTANT:** `READY_FOR_AI` is exactly the hand-off contract for the future AI Vision step.

**NEXT MODULE CONNECTION:** AI Vision (postponed) will consume only `READY_FOR_AI` images.

**TESTS:** `test_images.py` — three formats, empty/corrupted/misnamed files, resolution/blur/brightness classes, size limit, traversal payloads, uniqueness, zone isolation, metadata correctness (26 tests).
